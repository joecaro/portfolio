## What it is

Automated phone agents fail in ways no dashboard shows. A customer asks a reasonable question and the agent starts the payment over. Someone says they already paid and gets transferred. These problems are hiding inside tens of thousands of calls, and finding one used to mean listening to recordings until you got lucky.

Scout gives that job to an AI investigator. You ask a question, such as "Why do some customers get asked for their payment method twice?" The agent searches the calls by keyword and by meaning, groups them into cohorts that behave alike, maps where calls go in the conversation flow, and then reads the calls that matter, turn by turn. It writes down hypotheses as it goes, confirms or rejects each one, and finishes with a report.

The report is the product. Every finding names the exact turns behind it: what the agent was doing before, what the customer said, what the agent did wrong, and what it cost. It shows how many calls the finding reaches, which checks it passed and which it failed, and what the agent did not get to. If the evidence is not there, the honest result is "nothing supported," and Scout treats that as a real answer.

I built Scout on my own, from the first research experiment to the deployed service: the research harness, ingestion, embeddings, the search index, the agent tools, the service, the CLI and the report viewer. I designed it and made the calls; coding agents did much of the hands-on implementation under my direction.

## It started as a question: can a model find real problems at all?

Before building anything, I ran experiments on a frozen set of calls to find out what actually works.

**Cheap and stable beat expensive and clever.** I compared five ways of representing a call, from model-written labels of each turn to simple deterministic features computed from what the agent did. The deterministic features grouped calls about twice as consistently from run to run, and the model labels found nothing extra. So the cheap representation became the default.

**Finding candidates is easy. Proving them is the hard part.** In a matched benchmark, models flagged 74 positives on a first pass. When a second, independent model checked them, only 34 held up. More proposals did not mean more findings. That result set the shape of everything after it: Scout spends its effort on verification, not on generating ideas.

**So I made invented evidence impossible to submit.** The harness rejects a finding if it cites a call the agent never opened, a turn it never saw, a quote that does not match the source word for word, the wrong speaker, or a customer turn that does not come before the agent's reply. A fabricated finding fails that check before any person sees it.

## A big number is not a rate

One research result changed how every Scout report counts things. A literal search for a repeated prompt matched a huge number of calls, which looked like an epidemic. A stratified review of a sample found only a handful of real failures. Weighted back to the whole population, the actual problem was about 75 times rarer than the search count suggested.

Since then, Scout keeps its numbers separate: calls in the population, calls examined, calls matched, and calls actually read. It never merges them into one impressive figure. If coverage is unknown, a zero is reported as inconclusive, not as zero.

## Turning a research harness into a service

In mid-October I turned the harness into something other people could use:

- **Ingestion** that indexes calls with privacy checks and picks up where it left off after a failure.
- **A search index** with separate embeddings for conversation passages, runtime events and cohorts.
- **An agent API** that keeps every investigation inside one customer's data and rechecks the source each time it reads evidence.
- **A CLI and a report viewer** that journal each investigation and show it live while the agent works.

Speed mattered, because an investigator that waits two and a half minutes per step does not get used. The first server-side cohort build took 149 seconds. Precomputing each call's runtime profile next to its embedding brought it to about 28.

## Two failures in production, and what they taught me

**Search was timing out.** Hosted search began returning errors. I traced it to cold caches stalling for more than 50 seconds and to calls being loaded one at a time. Warming the index and loading calls in parallel batches brought the three failing searches down to 3 to 4.5 seconds each.

**One bad call could sink a whole batch.** A privacy check that rejected a single call escaped its handler and aborted every other call in the batch. I reproduced it with three synthetic calls, then isolated each call so one rejection affects only that call.

Both fixes follow the same rule as the rest of Scout: prove the cause before you fix it, and make sure a failure stays small and visible.

## How I know it works, and what I don't claim

Scout grades its own findings strictly. A finding counts as a supported problem only when it has the prior state, the trigger, the agent's response and the consequence, each tied to a verified source turn, plus evidence that the behavior was avoidable and harmful. Anything less is saved as an observation, not thrown away and not promoted.

Today Scout runs as a deployed service for internal staff, through the CLI and as the investigation engine inside Platform Chat. Its limits are real. The research checks used a second AI model, not human reviewers, so I have not measured accuracy against human judgment. A citation check proves the evidence exists, not that the conclusion is right. Some prevalence counts can still report a wrong zero, and that work is open.
