## What it is

Automated phone agents fail in ways dashboards don't show. A customer asks a reasonable question and the agent restarts the payment. Someone says they already paid and gets transferred. These bugs hide inside tens of thousands of calls, and finding one used to mean listening to recordings until you got lucky.

Scout hands that job to an AI agent. You ask something like "why do some customers get asked for their payment method twice?" The agent searches calls by keyword and by meaning, groups them into cohorts that behave alike, maps where calls go in the conversation flow, then reads the important ones turn by turn. It writes down hypotheses as it goes, confirms or rejects each one, and ends with a report.

Each finding in the report points to the exact turns behind it: what the agent was doing, what the customer said, what the agent got wrong, and what that cost. It also shows how many calls the finding covers, which checks passed and failed, and what the agent didn't get to. If the evidence isn't there, the answer is "nothing supported," and that counts as a result.

I built Scout myself, from the first experiment to the deployed service: research harness, ingestion, embeddings, search index, agent tools, API, CLI and report viewer. I made the design calls. Coding agents wrote a lot of the code.

## Can a model even do this?

Before building anything I ran experiments on a frozen set of calls.

First, how to represent a call. I tried five approaches, from model-written labels on every turn to simple features computed from what the agent actually did. The simple features clustered calls about twice as consistently from run to run, and the model labels didn't find anything extra. Cheap won.

Second, how good are models at spotting problems. In one benchmark, models flagged 74 positives on a first pass. A second, independent model checked them and only 34 held up. Coming up with candidates is easy. Proving them is the hard part, so that's where Scout spends its effort.

Third, I made fake evidence impossible to submit. The harness rejects a finding that cites a call the agent never opened, a turn it never saw, a quote that doesn't match the source word for word, the wrong speaker, or a customer turn that doesn't come before the agent's reply. Made-up findings fail before anyone sees them.

## Counts lie

One result changed how Scout counts everything. A literal search for a repeated prompt matched a huge number of calls and looked like a crisis. A stratified review of a sample found only a handful of real failures. Scaled back up to the whole population, the actual problem was about 75 times rarer than the search count suggested.

So Scout keeps its numbers separate: calls in the population, calls examined, calls matched, calls actually read. It never rolls them into one big number. And if coverage is unknown, a zero shows up as inconclusive.

## Making it a service

In mid-October I turned the harness into something other people could use: ingestion that indexes calls with privacy checks and resumes after a crash; a search index with separate embeddings for conversation passages, runtime events and cohorts; an agent API that keeps every investigation inside one customer's data and rechecks the source whenever it reads evidence; and a CLI plus a report viewer that shows the investigation live.

It also had to be fast, because nobody waits two and a half minutes per step. The first server-side cohort build took 149 seconds. Precomputing each call's runtime profile next to its embedding got it down to about 28.

## Two production bugs

Hosted search started erroring out. The cause was cold caches stalling for over 50 seconds, plus calls loading one at a time. Warming the index and loading calls in parallel batches got the three failing searches down to 3 to 4.5 seconds.

Later, a privacy check that rejected one call escaped its handler and killed every other call in the batch. I reproduced it with three synthetic calls, then isolated each call so one rejection only affects that call.

Same approach both times: find the cause before fixing anything, and keep failures small and visible.

## Does it work?

Scout is strict about what counts. A finding is a "supported problem" only if it has the prior state, the trigger, the agent's response and the consequence, each tied to a verified turn, plus evidence that the behavior was avoidable and harmful. Anything less gets saved as an observation.

It's deployed for internal staff, through the CLI and as the investigation engine inside Platform Chat. There are limits. The research checks used a second AI model instead of human reviewers, so I haven't measured accuracy against people. A citation check proves the evidence exists, not that the conclusion is right. And some prevalence counts can still come back as a wrong zero, which I'm still working on.
