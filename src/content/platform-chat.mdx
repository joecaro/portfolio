*Part of [Tools for Operating Voice Agents](/projects/voice-ai-platform), for exploring metrics and calls in one conversation.*

## What it does

Platform Chat lets staff ask questions about voice-agent activity, from a metric change to the calls behind it. It scopes the request, queries metrics, searches transcripts, reads relevant calls and returns links to the evidence. Users can follow the steps as they run. The default path is read-only; changes require confirmation.

## Carrying scope through the system

The first staging version exposed a basic failure: a follow-up asked about one campaign, but the answer was labeled “All Campaigns.” The conversation had retained the filter while the analytics query had not. I replaced message-level filter extraction with scope carried alongside the query, then added a check that compares query filters with the scope reported in the answer.

Another staging failure repeated the same invalid query while the panel stayed on “Thinking…” because progress was emitted only after the agent finished. I changed the runtime to stream each step, return readable errors, avoid retrying an identical failed query and preserve completed results if the final model response is malformed. Both prompts then worked in staging.

## One runtime for metrics and calls

The v2 runtime puts conversation state in durable storage and grants writes only to the current request owner. The service enforces customer scope, budgets, cancellation and deadlines; access tokens stay in server memory and are not sent to the model or logs. A skills-based runtime lets the model choose which domain capability to use while the server controls what that capability can access.

Metric names also need customer and campaign context. I built a catalog of 85 business concepts tied to their source and resolved by customer, campaign type, report and date. When the system cannot choose a definition, it asks for clarification. Review found an access-revocation path that could still serve a definition; I reproduced the issue, fixed it and added a regression check.

## Partial answers stay partial

A response can be incomplete when a source fails or a deadline expires. Each turn therefore ends with an explicit outcome such as completed, partial or needs clarification. The panel shows that outcome instead of implying success. Monitoring records execution details without retaining call content unless it is verified and in scope.

## Evaluation and status

The evaluation suite runs the real system against synthetic call data. Expected answers are hidden from the model and a separate reviewer grades each response. Sixty adversarial cases probe scope boundaries and access to unauthorized data; the latest run found no unsafe answers. Evaluations also found three defects before release, including a schema mismatch and citation-contract bugs.

Scores vary with rubric and fixture changes, so I do not present them as a trend. One 68-case run had 39 pass, 24 partial and 5 fail. Platform Chat runs in our main production environment. The evaluation figures above come from a specific test run. There are no customer adoption or time-saved measurements.
