## What it is

Teams that run automated phone agents make tens of thousands of calls. When a number moves, someone has to find out why, and that used to mean a dashboard, a SQL query and an afternoon of listening to recordings.

Platform Chat is a side panel that opens beside whatever page you are on. You ask a question in plain English: "Why did transfers go up this week?" or "Find calls where the customer disputed the balance." The assistant works out the scope (which campaign, which dates, which calls), counts the population, searches the transcripts, reads the calls that matter, and answers. The answer links to every call it relied on, and a short line underneath says exactly what it looked at. You watch it work the whole time, step by step.

It is read-only. It cannot change anything without asking.

I led it from the first prototype to the version running today: the product shape, the architecture, the safety model, the evals, and the UI. I worked the way I now build most things: I set the design and the contracts, directed coding agents to implement in parallel, had separate agents review their work, and verified the result myself before anything merged.

## Version one taught me what could go wrong

The first version, in August, was a narrower analytics chat that answered metric questions. I had it running on a staging environment within two days. The bugs it exposed shaped everything after.

**A follow-up silently answered a bigger question.** A user asked about one campaign, then asked a follow-up. The answer came back labeled "All Campaigns." The conversation knew the scope; the query did not. Filters were being pulled out of the latest message with pattern matching, and the answer's provenance dropped them. A wrong number from an analytics assistant looks exactly like a right one, so I made this a hard rule: scope travels with the query, and a check fails if the query's filters and the answer's stated filters differ by a single value.

**Progress arrived after the work was done.** On staging, a query referenced a table under the wrong schema and failed over and over. The interface showed only "Thinking…" the whole time, because progress events were sent after the agent finished. I streamed every step as it happened, saved readable failure details, stopped the agent from retrying an identical failed query, and kept a completed result when the model's final message came back malformed. Both prompts that had failed returned correct, evidence-backed answers the same night.

**Unit tests passed while the real model failed.** Mocked tests were green while the deployed model misbehaved. So I added a live-model behavioral eval that needs no production data. That idea became the backbone of the next version.

## One path, not five

By October the goal was bigger: one conversation that could answer metric questions and investigate individual calls. There were already several half-built engines, routing layers and chart pipelines to choose from. I had three independent analyses written, had them argue against each other, and chose the simplest shape that could be made safe:

- **One durable request path.** Every turn is saved as it runs, and only the current owner of a request can write to it. A crash or a duplicate delivery cannot corrupt a conversation.
- **The host holds the power, not the model.** Tenant scope, budgets, cancellation and deadlines are enforced by the service. The user's access token stays in server memory and never reaches the model or the logs.
- **Everything else was deleted.** The warm engines, alternate routers and extra chart paths went away. Fewer paths meant fewer places for scope to leak.

A few days later I replaced separate specialist processes with one main prompt, a small set of domain skills the model can discover, and a narrow capability API the host enforces. The model decides what to look at; the host decides what it is allowed to touch.

## Shipping a large change so people could actually review it

The consolidated system was too big to review as one change. I split it into 19 stacked pull requests, each sized to one dependency: scoped request authority, the tool layer, the durable service and API, the eval harness. Each layer was reviewable on its own, and the assembled stack passed 214 tests on day one. The suite has since grown to about 1,250.

## Teaching it what words mean

The same metric name can mean different things on different kinds of campaigns. A generic definition gives a confident, wrong answer. I built an ontology of 85 business concepts, each traced to a source and resolved by customer, campaign type, reporting surface and date. If the scope is unknown, the concept stays unresolved and the assistant asks, instead of falling back to a default.

Review of that work found three real defects, all reproduced before the fix and passing after:

- A rate lookup with no campaign type resolved to one specific definition anyway.
- A locally stored definition could come back before the access checks ran, so it could still be served after a user's access was revoked.
- Discovery silently stopped at 20 concepts. It now says when a list is truncated.

## Saying "partial" out loud

A response can arrive successfully and still be incomplete: the model ran out of time, or one source failed. Every turn now ends with an explicit outcome: completed, partial, needs clarification, interrupted, deadline reached, or fallback. The UI shows it. "Deadline reached" only appears when the real deadline actually expired. A stopped turn says "Partial results do not establish a complete answer." Tracing follows the same rule: it records IDs, names and token counts, and withholds call content unless it matches complete, in-scope evidence.

## How I know it works, and what I don't claim

The evals run the real coordinator, runtime and tool permissions against synthetic call data, with expected answers kept out of the model's context and every answer graded by an independent reviewer. There are 329 cases across 12 catalogs, including 60 adversarial cases that try to break scope and pull data the user should not see. All 60 passed after the last round of fixes.

The harder gates are not all green, and I report them that way. The latest focused 68-case run graded 39 pass, 24 partial and 5 fail. Partial answers are the work in front of me, and I haven't claimed an overall improvement I can't show.

Today Platform Chat runs as a staff preview behind sign-in and an internal-user gate. It has not had customer production traffic yet, so I have no adoption or time-saved numbers to report.
