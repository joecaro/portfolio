## A local control room

I built this personal tool to coordinate coding-agent runs across separate Git worktrees. A manager turns a goal into a plan; workers implement tasks; reviewers inspect deliveries; and I approve a saved patch before it is merged. The browser interface shows the dependency graph, workers, worktrees and delivery state together.

It remains a single-user project, not a shared product.

## Recovering from worker loss

The app recorded 534 jobs: 160 implementation runs, 136 reviews and the remainder chat. Eighty-three implementation or chat runs were recovered after their workers were lost. Reviews do not resume automatically; a lost review must be rerun. The counts describe this app's job history, not time saved or team adoption.

Each job is persisted with a lease and heartbeat. When the lease expires, a recoverable run returns to the queue with its attempt count updated, or ends as lost with a reason. Finished runs save their diff as a patch file so work can survive worktree deletion.

## One source for runtime state

Completed work twice continued to appear as “running”: first because live counters included finished jobs, then because a saved summary lagged behind orchestration state. I moved runtime state into SQLite as the authority and made Markdown an import/export format. The interface now derives status from current job records rather than relying on an older summary copy.

## Approve the patch that was reviewed

An approval is bound to one run's saved patch. If a newer run exists for the same task, the old snapshot cannot be merged. The merge gate also reserves its target before asynchronous work begins, preventing two approvals from racing on the same branch.

The destination checkout is checked separately from the worker worktree. Uncommitted changes block a direct merge; a requested stash is refused if files changed since review. A multi-repository integration failure rolls back the integration worktree.

## Status and limits

I ran 511 of the 534 jobs in June. The clearest payoff in the job history was recovery after a worker disappeared: the queue recovered 83 implementation or chat runs. I added plan approval in July and tested it, but used it for one plan outside those tests. I was the only user. The demo uses fictional jobs.
