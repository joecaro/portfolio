## What it is

In June 2026 I got tired of running coding agents one terminal at a time, so I built a control room for them. It's a local web app. I give it a goal, a manager agent turns that into a plan, and once I approve the plan it starts workers, each in its own Git worktree. Separate reviewer agents check the work. When something is ready, I approve one exact saved patch and the app merges it.

The browser is the main interface on purpose. I considered a terminal UI and decided against it, because the whole point is seeing a lot of moving parts at once: the plan as a dependency graph, which workers are active, which worktrees exist, and where each delivery is (submitted, accepted, integrated, validated).

It's a personal project and I'm the only person using it. Much of the code was written by the agents it runs, from tasks I wrote and reviewed.

Starting agents was easy. Most of the work went into keeping the app's picture of what was going on accurate while runs crashed, retried and finished out of order.

## Crashes are normal

Over its life the app ran 534 agent jobs: 160 implementation runs, 136 reviews, and the rest chat runs. 83 of them lost their worker and got picked back up automatically. Most of those (60) were from me restarting the server mid-run; the other 23 had their lease expire while running. Another 15 ended as lost: 11 after their retry, and 4 reviews, which never get one.

So every job is a row in a database with a lease and a heartbeat (45 seconds and 5 seconds). If the lease runs out, the job goes back in the queue with its attempt count bumped, or it ends as "lost" with a reason. It never just vanishes. Each finished run also saves its diff as a patch file, so if a worktree gets deleted the work can still be recovered.

One gap: only implementation and chat runs resume automatically. A review that dies ends as lost and has to be rerun from scratch.

## The bug I fixed twice

Finished work kept showing as "running." The first time, the counters were including runs that had already finished, so I made "running" come only from live jobs. Then it came back in a different form: a saved summary still said "running" after the orchestration underneath it had completed. That fix landed about six weeks after the first.

The rule I ended up with: a saved summary is just a copy, and when it disagrees with newer evidence, the evidence wins. In July I made SQLite the one source of truth for runtime state and turned the old Markdown files into import and export only. Fewer copies, fewer chances to disagree.

## Approving the right thing

Agents revise their work, so approving yesterday's patch says nothing about today's. The merge gate approves one run's saved snapshot. If there's a newer one for the same task, it refuses and tells me to approve the latest run instead.

Approvals can also race. Two of them could both check "is a merge already running on this branch?", both see no, and then both change the same target. Now the gate reserves the target before it does anything asynchronous and holds it until the merge finishes. A second approval gets a clear "target branch already has active merge."

## My checkout matters too

Worktrees protect my checkout from the agents. They don't protect the agent's patch from my checkout. So the gate checks the destination separately. Uncommitted changes block a direct merge. If I choose to stash them, it refuses when the dirty files have changed since I last looked, so it never stashes something I haven't seen. If a merge across several repos fails halfway, it rolls the integration worktree back.

## Where it stands

Use peaked in June (511 of the 534 jobs). The plan-approval layer I added in July has tests but has only run one real plan. These numbers come straight from the app's database and don't measure time saved.
