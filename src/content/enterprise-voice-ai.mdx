*Part of [Tools for Operating Voice Agents](/projects/voice-ai-platform), for testing agent changes before release.*

## Comparing agent runs

Enterprise voice agents verify callers, take payments and transfer calls. Before changing an agent, engineers need to compare its behavior across test cases and repeated attempts. I worked across the evaluation console, comparison APIs, tool-result capture, case catalog and selected call-state fixes.

The console presents test cases as rows and runs as columns. Each cell shows the attempts and opens a detail view with expected behavior, grader explanation, tool activity and transcript. Results such as not run, ungraded, incomplete and failed remain distinct, so infrastructure or evaluation gaps do not silently become agent failures.

## Keep ad hoc runs out of release history

Engineers needed to rerun a single case while debugging. Initially, that scratch run appeared as a full run in the tracked grid, making an 889-case suite look almost entirely empty. I separated scratch and tracked views using an existing run-type field. Scratch results cannot change a tracked verdict, and retrying a small batch reads that batch's own case IDs rather than widening back to the full suite.

## Define what can be compared

The comparison API counts a case only when both runs used the same case version, completed without errors, graded all attempts and scored the same number of attempts. It reports excluded cases by reason alongside the comparison. A result such as “4 fixed, 1 regressed” therefore also identifies the cases that could not be compared.

For tool evidence, the runner snapshots tool executions before each turn and associates newly completed results with calls by tool name and, when needed, arguments. If the association is ambiguous, it attaches nothing rather than guessing. Sensitive output is redacted.

Case identity connects history across runs. The loader collapses exact duplicates and rejects ambiguous names or duplicate IDs. A failed catalog sync prevents the service from reporting ready. This also exposed inbound and outbound cases that had incorrectly shared an identity.

## Additional call-state fixes

I fixed late disconnect cleanup, isolated tracing between calls in a long-running worker, and prevented delayed transfer events from changing the state of a later transfer. The transfer adapter retains retired transfer IDs and ignores their late events. Regression tests cover these state transitions. The changes were pushed, but I have not confirmed that they deployed.

## Status

Engineers use the console to run test suites; I do not have usage counts. The work spans release and feature branches, and I have not verified which components are on main. The demo above reconstructs the console with fictional cases and runs.
