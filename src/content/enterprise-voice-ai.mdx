## What it is

Enterprise phone agents do real things: verify a caller's identity, take a payment, transfer to a person. Before a new version ships, someone has to answer "is this version better or worse than the last one?" across hundreds of test cases. Getting that number right is harder than it sounds.

I worked on the testing side: an evaluation console where engineers run test suites and compare results, the APIs that decide which results are comparable, the code that captures what each tool call actually returned, the catalog of test cases, and a few bugs in how the live call system handles state.

Much of the code was written with coding agents. I designed the pieces, reviewed the work, and chased the bugs.

## The console

The main screen is a grid. Rows are categories that expand into test cases. Columns are runs, newest on the left. Each cell shows every attempt as a tick, so you can see at a glance whether a case passed three times or passed once and failed twice. Click a cell and a drawer opens with the expected behavior, the grader's reasoning, the tool calls, and the transcript, compared against the nearest older run that has a result.

A few rules shaped it:

- "Didn't run," "not graded," "didn't finish" and "failed" are four different things, and each gets its own label. An infrastructure error is not the agent failing.
- Each state gets exactly one color. Pass rates stay plain black on purpose. There's no real threshold to color them against, and a green 82% invites a conclusion nobody earned.
- A cell that changed since the previous run gets a mark that doesn't rely on color.

The first version had bugs that all made results look better or worse than they were. The detail panel said "Baseline passed" no matter what the baseline did. A row where nothing had been graded was labeled "always fails." And "changed since baseline" was comparing against the wrong column. All fixed, and they're why the console is so fussy about labels now.

## Scratch runs

Engineers wanted to rerun one case quickly while debugging. The first time someone did, it added a whole new column to the grid that was about 99% empty, out of 889 cases, and it sat in the record next to the real runs.

I split quick runs from tracked runs. The data already had a run type field that scoped the grid, the metrics and the verdicts, so I used that instead of adding a new flag and a migration. A scratch result never changes a case's verdict, and rerunning a batch reads that batch's own case IDs, so retrying three cases can't accidentally turn into 889.

## What counts as comparable

When comparing two runs, the API only counts a case if both runs used the same version of it, neither had errors, neither had ungraded attempts, and both scored the same number of attempts. Everything else is left out and reported as excluded, by reason. So "4 fixed, 1 regressed" comes with "and 7 we couldn't compare, here's why."

Cases where the agent never reached the behavior being tested got their own outcome too, and they don't count toward the score.

## Capturing what tools returned

A test that checks the agent "called the payment tool" isn't worth much if you can't see what the tool said back. So I made the test runner record each tool's return value. Before each turn it takes a snapshot of tool executions, then matches new ones by tool name, and by arguments when the same tool runs twice. If it still can't tell which execution belongs to which call, it attaches nothing rather than guess. It only attaches finished executions, and it redacts sensitive data from the output.

## The case catalog

Test cases come from a shared catalog file. The loader collapses exact duplicates, fails if two variants share a name without explicit IDs, fails on duplicate IDs, and blocks the service from reporting ready if the sync fails. Later I split inbound and outbound cases that had ended up sharing one identity.

## Call-state bugs

A few fixes on the live call side, all about events showing up at the wrong time:

- A caller disconnecting after cleanup had already run used to trigger a second cleanup. We saw duplicate cleanup in a staging test. Now the late event keeps its telemetry but doesn't clean up again.
- Tracing in the long-running worker process is now isolated per call, so one call's trace can't bleed into the next.
- Delayed events from a finished transfer could change state on a later one. The adapter now remembers retired transfer IDs and ignores late events for them. Three regression tests fail against the old code and pass against the new; the full suite was 123 passed, 1 skipped. That fix was pushed to the merge branch, but I didn't confirm the deploy to the test environment.
